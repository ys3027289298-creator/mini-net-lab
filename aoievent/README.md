# aoievent

按半径每帧求可见集，与上一帧求差，把进/出事件按 **(帧号, 实体序)** 投递到
有界 FIFO；队列满时尾部丢弃并累计丢弃数。`make test` 跑自检。

## 数据流

1. `watcher_tick` 帧号自增，按半径（含边界 `d <= r`）扫描全部实体得到当前可见集。
2. 与上一帧可见集求差，单次按实体槽位（插入序，删除只置墓碑，槽位不回收）扫描，
   进入 / 离开事件按槽位序混入同一帧，不把离开整批排在进入之前。
3. 事件入有界队列，`evq_pop` 按 FIFO 取出，即按帧号升序、同帧按实体槽位升序投递。
4. 入队满则丢弃新事件并累加 `dropped`；可见集真相照常更新，投递与真相解耦。

## 为什么消费端不会先看到离开后看到进入

设消费端按 ENTER 加载、LEAVE 卸载，实体槽位 s 的事件链只可能为
`ENTER, LEAVE, ENTER, ...`。

1. **帧级来源**：ticks 按帧号递增执行，后一帧产生的事件不可能先于前一帧入队。
2. **帧内来源**：一帧之内槽位 s 至多出一个事件（可见集是集合，状态只可能在
   在/不在之间翻转一次），且所有事件按槽位升序入队。
3. **队列不换序**：FIFO 只做入队/出队，溢出是丢弃而非重排；丢弃后投递流仍是理想
   有序流的一个**子序列**，不改变任意两个幸存事件的相对顺序。
4. 因此对任意槽位 s，幸存事件在投递流中仍保持 `ENTER` 先于对应的 `LEAVE`
   （归纳：初始不可见；每次 `ENTER` 前一事件必为 `LEAVE` 或流首，且两者顺序不被
   换序），消费端不会在没有已加载实体的情况下收到 LEAVE。

注意：如果对应 ENTER 本身被溢出丢弃，LEAVE 到达时消费端确实没有该实体——这是
丢弃造成的**信息缺口**，不是顺序错乱。应用应把非零 `dropped` 视为需要全量重同步
的信号；顺序保证只约束未丢弃事件之间的次序。

## 反例测试（`lifo_leave_before_enter`）

构造两帧：f1 实体 7 在半径内产生 `ENTER`，f2 移出产生 `LEAVE`，两事件都在队列中。
- 正确 FIFO：先 ENTER 后 LEAVE，消费端违例计数为 0（`fifo_no_violation`）。
- 错误的 LIFO 投递（反例）：先弹出 f2 的 LEAVE，消费端对未加载实体收到 LEAVE，
  `leave_before_enter = 1`（`lifo_leave_before_enter`）。

即“入了队但投递顺序不保证帧序”的实现会在该用例下直接暴露问题。

## 其余自检

- `matches_full_scan_oracle`：60 帧随机移动，与独立的逐帧全量重算 + 集合差
  参考实现逐事件比较（帧号、槽位、类型、id 全一致）。
- `delivery_frame_slot_order`：投递流严格按帧号非降、同帧槽位严格升序。
- `consumer_never_leave_first` / `consumer_set_matches_visible`：消费端无
  LEAVE 前置、无重复 ENTER，终态活动集与可见集一致。
- `overflow_tail_dropped` / `overflow_preserves_order` /
  `dropped_counter_cumulative`：16 深队列投递 20 个事件，丢 4 个并计数，
  幸存事件顺序不变，丢弃数跨帧累计。
